## Ambiguity hardening backlog

Added 2026-08-24 after reviewing the English-memory regression and 77 recent Phoenix traces. The
production sample is dominated by long diagram/tool-discovery workflows, project-memory reads,
cross-turn canvas work, repeated icon searches, proposal acceptance, and verification reads.
Representative trace patterns: `6444821a840936b462bfcd052aeae598`,
`b91b56c042e674665520655dfde415d4`, `8f83854b647039acffec7c28c6086abb`, and
`b2b637b0f79e60a816df16a7c8b46e53`. New cases must use synthetic data and generic phrasing rather
than copying private prompts or note content.

Hard-case rules:

- Ambiguity is deliberate: prompts should state a human goal without naming the expected tool.
- A case must contain enough evidence for one contractually correct outcome; ambiguity must not mean
  the fixture has no answer.
- Prefer persisted effects, ordering, scope, and absence of collateral changes over tool-name-only
  assertions.
- Keep confusable alternatives in the fixture or catalog so keyword matching is insufficient.
- Include negative twins where the same surface wording lacks the fact that authorises an action.
- Never simplify a failed prompt merely to induce the expected call. Repair invalid contracts, then
  strengthen the end-state assertion.

Reporting rule: section pass rates are acceptance results, not a single measure of model improvement.
The final report must classify every material green-producing change as one of: model/runtime behavior,
tool exposure or retrieval, harness/oracle correction, fixture-contract correction, or prompt/case scope
change. Correcting an invalid test proves only that the harness now measures the production contract.
Making an ambiguous prompt more explicit changes the tested behavior and must never be counted as an
ambiguity improvement; prefer restoring the ambiguity with an effect-backed oracle.
