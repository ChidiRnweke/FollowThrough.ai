title: Writing API docstrings
description: The docstring standard behind the generated API reference.
---

The [API reference](/FollowThrough.ai/reference/) is generated by TypeDoc from docstrings, and the build hides any public symbol that is not documented. That makes the docstring standard part of the delivery pipeline, not a style suggestion.

## The standard

Three rules, in order of importance:

**Say why, not what.** A function named `render_tree` does not need a docstring that says it renders a tree. It needs one that says why it exists and what is non-obvious about it: *renders the tree, and is called concurrently because it is part of a forest*. If a reader could have inferred the summary from the name and signature alone, the docstring is noise.

**Capture the edge cases and invariants the code encodes.** The most valuable docstrings document what the code does *not* do: the transaction that reconciles links on save, the idempotency key that makes retries safe, the rejection instead of clamping of out-of-range limits. These are the facts a caller cannot guess.

**Keep it short.** One summary paragraph plus `@param`/`@returns`/`@throws` where they add information. A domain term is defined once, on first use.

## What to document

Docstring effort follows the layers that the reference exposes:

1. **Controllers** — the `<Capability>Controller` interface (the contract) and its `<Capability>Dependencies`.
2. **Service contracts** — the `contracts.ts` interfaces services expose.
3. **Factories and models** — composition functions and zod schemas (schemas get field descriptions, not essays).

Internal implementation files — repository adapters, spec files — are excluded from the reference and need no docstrings.

## How the build enforces it

`docs/astro.config.mjs` configures the TypeDoc plugin with `excludeNotDocumented`, so the reference only contains documented symbols. Adding a public method without a docstring does not fail the app build; it silently drops the symbol from the docs build. Run the docs build locally to see exactly what a change exposes:

```bash
pnpm -F @followthrough/docs build
```

## Example

A controller method with the *why* written down:

```ts
/**
 * Record approvals or rejections for several pending tool calls and requeue the run.
 *
 * The batch is all-or-nothing: every call id must currently be pending, otherwise
 * nothing is recorded. A partial batch against a run that then requeues would leave
 * the user staring at approval cards whose decision silently went nowhere.
 *
 * @throws ValidationError if the run is not awaiting approval or any call id is not pending.
 */
decideMany(actor: ActorContext, input: DecideAgentRunBatchInput): Promise<AgentRunSnapshot>;
```

The name and types already say what it does. The docstring earns its place by saying why a batch is atomic and what happens if it is not.
