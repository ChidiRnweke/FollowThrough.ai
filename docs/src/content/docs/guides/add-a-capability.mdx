## TL;DR

A new capability touches the same six places every time: a model module, a repository contract plus its Postgres implementation, a service, a controller, one capability factory, and a delivery boundary. Build them in that order, wire the factory into `src/lib/server/application.ts` in dependency order, document every public controller method, and prove the graph still holds with `pnpm test:architecture`.

## Intent

This guide is the recipe for adding a capability that passes the architecture checks on the first run. The layering rules themselves are explained in [Architecture](/FollowThrough.ai/explanation/architecture/); here we only care about doing it.

The running example is `skills` — small, real, and easy to read end-to-end.

## Where each piece lands

<FileTree>
- src/
  - lib/
    - models/skills/index.ts — types and branded IDs, a leaf module
    - server/
      - db/schema/registry.ts — Drizzle tables, re-exported from schema/skills.ts
      - repositories/skills/
        - skills.ts — the SkillRepository contract
        - index.ts — barrel re-export
        - postgres/skills.ts — SkillRecords, the Drizzle implementation
      - services/skills/
        - contracts.ts — role interfaces (SkillFinder, SkillCreator, …)
        - library.ts — the implementation
      - controllers/skills/controller.ts — SkillsController, the documented surface
      - skills-capability-factory.ts — createSkillsCapability
      - application.ts — composition root
  - routes/… — pages that call the remote functions
  - lib/remote/skills/skills.remote.ts — delivery boundary
</FileTree>

## The recipe

<Steps>

1. **Model — `src/lib/models/<cap>/index.ts`**

   Define the capability's types and branded IDs. The model is a leaf module: it never imports another capability's model. Foreign IDs are redeclared as local structural aliases — the skills model declares its own `NoteId` and `ProjectId` brands rather than importing them (`src/lib/models/skills/index.ts:3-7`), so capabilities stay decoupled at the type level.

2. **Repository — `src/lib/server/repositories/<cap>/`**

   Persistence needs three files plus a schema table:

   - The contract, e.g. `SkillRepository` in `repositories/skills/skills.ts` — a plain interface, no Drizzle types in its signatures.
   - A barrel `index.ts` that re-exports the contract.
   - The Postgres implementation in `postgres/<cap>.ts`, e.g. `SkillRecords implements SkillRepository` (`repositories/skills/postgres/skills.ts`). This is the only place Drizzle and SQL exist, and it maps rows to models immediately (`toSkill` from `$lib/server/db/mappers`) — nothing above the repository ever sees a database row.

   Declare the tables in `src/lib/server/db/schema/registry.ts`, re-export them from `schema/<cap>.ts`, then generate the migration:

   ```bash
   pnpm db:generate
   ```

3. **Service — `src/lib/server/services/<cap>/`**

   Put the business rules here. `contracts.ts` holds the interfaces the rest of the world depends on — keep them small and role-shaped (`SkillFinder`, `SkillCreator`, `SkillEditor`, … in `services/skills/contracts.ts`) so controllers inject only what they use. The implementation classes satisfy those interfaces. A service imports models and repository contracts only — it never imports another service.

4. **Controller — `src/lib/server/controllers/<cap>/controller.ts`**

   One file, three exports, following `controllers/skills/controller.ts`:

   - `SkillsController` — the interface, one method per operation, taking an `ActorContext` and an input. This interface is the product's public surface: it is what the [API reference](/FollowThrough.ai/reference/) renders, so every method needs a docstring (see step 8).
   - `SkillsDependencies` — every service role the controller needs, injected so it can be built and tested without real stores.
   - `class Skills implements SkillsController` — thin orchestration. It coordinates services and wraps multi-step work in `transactionRunner.run(...)`; it makes no domain decisions itself.

   Then register it in the factory types: add a `<cap>(): <Cap>Controller` method to `ControllerFactory` (`src/lib/server/controller-factory.ts`) and implement it in `ProductionControllerFactory` (`src/lib/server/production-controller-factory.ts`), adding your dependencies to `ProductionControllerDependencies`.

5. **Capability factory — `src/lib/server/<cap>-capability-factory.ts`**

   Export exactly one `create<Capability>Capability` function. It takes the database plus the *other capabilities' repositories and services* it depends on, constructs this capability's repository and services, and returns them — nothing else. The real thing, from `src/lib/server/skills-capability-factory.ts:24`:

   ```ts
   export const createSkillsCapability = (input: SkillsCapabilityInput): SkillsCapability => {
   	const repository = new SkillRecords(input.db);
   	const library = new SkillLibrary(
   		repository,
   		input.notes,
   		input.provenance,
   		new SkillManifestCodec()
   	);
   	// …
   	return { library, builtIns, provisioned: new BuiltInSkillLibrary(builtIns, library) };
   };
   ```

   Note what the factory does *not* do: it does not build the controller. Controllers are constructed per request by `ProductionControllerFactory` from the dependency object you wire in the next step.

6. **Compose — `src/lib/server/application.ts`**

   Two edits in `createApplication`:

   - Call your factory in dependency order — after every capability it consumes, before everything that consumes it. Skills sits after notes and projects (`application.ts:150`):

     ```ts
     const skillCapability = createSkillsCapability({
     	db,
     	projects: projectCapability.repository,
     	notes: noteCapability.repository,
     	provenance: noteCapability.provenanceRepository
     });
     ```

   - Add the controller's entry to the `dependencies` object passed to `ProductionControllerFactory`, mapping each service role to the instance that satisfies it (`application.ts:392-403`).

   <Mermaid
   	source={`
   flowchart TB
   	app["application.ts"] --> factory["createSkillsCapability()"]
   	factory --> repo["SkillRecords — postgres adapter"]
   	factory --> service["SkillLibrary — service"]
   	app --> controllers["ProductionControllerFactory"]
   	controllers --> controller["SkillsController"]
   	service -. implements .-> contract["SkillRepository contract"]
   	repo -. implements .-> contract
   	controller -. depends on .-> service
   `}
   />

7. **Delivery boundary — `src/lib/remote/<cap>/` or a route**

   Delivery code delegates to controllers; it contains no logic of its own. The remote-function boundary validates input with zod, resolves the actor, and calls the controller — see `src/lib/remote/skills/skills.remote.ts:11`:

   ```ts
   export const toggleSkill = command(z.object({ noteId, enabled: z.boolean() }), async (input) => {
   	await AppFactory.controllers()
   		.skills()
   		.update(requestActor(), {
   			noteId: input.noteId as NoteId,
   			isEnabled: input.enabled
   		});
   	return { enabled: input.enabled };
   });
   ```

   Server load functions and form actions in `src/routes/` follow the same rule: resolve the actor, call the controller, render the result.

8. **Document the public surface**

   Every method on your `<Capability>Controller` interface needs a docstring that says *why*, not what — the docs build drops undocumented symbols from the reference silently. The standard and real examples are in [Writing API docstrings](/FollowThrough.ai/guides/write-api-docstrings/).

</Steps>

## Verify

```bash
pnpm test:architecture
```

Three checkers run, and each catches a different way this recipe goes wrong:

- **Topology audit** (`scripts/audit-topology.ts`) — a service importing another service, a model importing across capabilities, SQL outside a repository, a factory with the wrong shape.
- **Test-quality audit** (`scripts/audit-tests.ts`) — mocks or spies in server-layer tests; hand-written fakes only.
- **chisel** (`chisel-js check`) — the remaining architecture and design-system invariants.

A red run names the file and the rule. Fix the import, not the checker.

<Aside type="tip">

If you are unsure how a piece should look, read the skills capability top to bottom — model, contract, adapter, service, controller, factory, remote functions. It is the smallest complete example of every rule on this page.

</Aside>
