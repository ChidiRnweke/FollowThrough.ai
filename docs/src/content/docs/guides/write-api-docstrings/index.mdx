## TL;DR

The [API reference](/FollowThrough.ai/reference/) is TypeDoc-generated from the controller, service-contract, and factory sources, and the build runs with `excludeNotDocumented` — an undocumented public symbol does not warn, it vanishes. Write docstrings that say *why* a method exists and which invariants callers rely on, in as few words as that takes.

## Why the standard is enforced by deletion

`docs/astro.config.mjs` points starlight-typedoc at exactly the public surface (`astro.config.mjs:86-91`):

- `src/lib/server/controllers/**/controller.ts`
- `src/lib/server/services/**/contracts.ts` and `catalog.ts`
- `src/lib/server/**/*-factory.ts`

and sets `excludeNotDocumented: true` for classes, interfaces, methods, properties, functions, and type aliases (`astro.config.mjs:107-121`). TypeDoc drops any of those that lacks a doc comment. So adding an undocumented controller method does not fail a build or annoy a reviewer — the method simply never appears in the reference, and the public surface documented on this site silently diverges from the code. The docstring *is* the publishing step.

<Aside type="caution">

Internal files — repository Postgres adapters, service implementations, spec files — are not entry points, so they never reach the reference. Docstrings are required only on the contracts: the `<Capability>Controller` interface and its methods, service role interfaces, and capability factories.

</Aside>

## The standard

Three rules, in order of importance:

**Say why, not what.** The name and signature already carry the *what*; TypeDoc renders them for free. A docstring that restates them is noise. Spend the words on what a reader cannot infer: why the method exists as a separate operation, what side effect it has, what it deliberately does not do.

**Capture the invariants callers rely on.** The most valuable docstrings document the guarantees and edge cases encoded in the code: the batch that is all-or-nothing, the idempotency key that makes retries safe, the read that is *not* side-effect-free. These are the facts a caller cannot guess from types, and the ones that break integrations when they change.

**Keep it short.** One summary sentence, a second paragraph only when the *why* needs it, and `@param` / `@returns` / `@throws` only where they add information the types don't. If you need more than a short paragraph, the complexity probably belongs in a subsystem page, not a docstring.

## Real examples

Each of these is quoted from the codebase and is what the reference renders today.

**Explain a side effect the name hides** — `SkillsController.loadForAgent` (`src/lib/server/controllers/skills/controller.ts:39`):

```ts
/**
 * Load a skill for the agent and record that it was used.
 *
 * Distinct from {@link get} because loading by the agent is a side effect: it writes
 * a usage record linking the skill to the note it was applied against, which is what
 * makes "which skills actually get used" observable later.
 */
loadForAgent(actor: ActorContext, input: LoadSkillInput): Promise<SkillView>;
```

A caller who reached for this instead of `get` by name alone would write usage records unintentionally. The docstring exists to prevent exactly that mistake.

**Document an invariant and its failure mode** — `AgentController.decideMany` (`src/lib/server/controllers/agent/controller.ts:137`):

```ts
/**
 * Record approvals or rejections for several pending tool calls and requeue the run
 * for continued execution.
 *
 * The batch is all-or-nothing: every call id must currently be pending, otherwise
 * nothing is recorded. A partial batch against a run that then requeues would leave
 * the user staring at approval cards whose decision silently went nowhere.
 *
 * @throws ValidationError if the run is not awaiting approval or any call id is not
 * pending.
 */
decideMany(actor: ActorContext, input: DecideAgentRunBatchInput): Promise<AgentRunSnapshot>;
```

The signature says the method batches decisions. Only the docstring tells you the batch is atomic, *why* it must be, and what throws when it is not.

**Document the contract, not just the methods** — the interface-level comment on `SkillsController` (`src/lib/server/controllers/skills/controller.ts:27`):

```ts
/**
 * Application boundary for skills: reading, creating, editing, and versioning the
 * skill notes the agent can load.
 *
 * Skills are just notes with extra metadata, so creation and versioning go through the
 * note subsystem; `get` is a pure read, while the agent-facing load also records usage.
 */
export interface SkillsController {
```

Interface docstrings are the landing text for the module's reference page. Two sentences that place the capability in the system save a reader from reconstructing it from ten method signatures.

## See what the reference actually renders

The docs site is the `@followthrough/docs` workspace package. Preview the reference locally while you write:

```bash
pnpm -F @followthrough/docs dev
```

and run the full build before opening a pull request — it is the only place a silently dropped symbol shows up, as an absent page:

```bash
pnpm -F @followthrough/docs build
```

If a method you just added is missing from `http://localhost:4321/FollowThrough.ai/reference/`, the cause is almost always a missing docstring, not a TypeDoc misconfiguration.
