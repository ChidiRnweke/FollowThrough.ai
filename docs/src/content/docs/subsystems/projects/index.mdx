---
title: Projects
description: Project scope, folder creation and transactional tree moves.
---

A project scopes notes, tasks, attachments and other workspace records. Active project names are
unique per account, ignoring case. Folders are note records with kind `folder`; skills share the
same table but do not appear in the project tree.

## Ownership

- **Models** define project values, request types and Zod schemas.
- **Shared services** normalize project details and assemble project trees. Browser and server
  controllers apply the same rules.
- **ProjectCatalog** reads and persists projects and validates tree moves against current entries.
- **Projects** coordinates those services and owns the move transaction.
- **Notes, Projects and Skills** each coordinate document creation. Each controller reads project
  and parent facts through NoteCatalog, applies the shared note-creation rule and persists through
  NoteCatalog.
- **ProjectRecords** owns SQL for projects and tree ordering. **NoteRecords** owns document creation,
  including folder records.

## Creation and project scope

Creation requires an explicit project. A missing or foreign project fails; creating a note or folder
does not choose another project or create one as a fallback. A parent must be an active folder in the
same project. Titles are trimmed and cannot be blank.

Notes, folders and skills use the same stored sibling count for their initial position. Archived
siblings remain part of that count. Offline commands use the same creation rule with downloaded
facts; the server resolves authoritative facts before writing. Caller-assigned identities survive
synchronization so children can reference a folder created offline.

## Tree moves

Projects runs a move inside its transaction. ProjectCatalog rejects a negative or non-integer
position, a document parent, self-parenting and a move below a descendant. It preserves sibling order
and clamps a position beyond the target list to its end. ProjectRecords persists both affected
sibling lists. A root move writes SQL NULL for the parent so a reload retains root placement.

The transaction prevents partial ordering writes. Concurrent tree moves still need a separate
locking review; these checks do not establish serialization of competing moves.

## Project details and archive

Controllers apply the shared detail rule before persistence. Names and descriptions are trimmed;
blank names fail. Clearing a description writes SQL NULL. The database enforces active-name
uniqueness per account, ignoring case. Archiving releases the name.

Project reads exclude archived projects. Tree reads return active note records ordered by position
and creation time. The shared tree presentation excludes skills. Folder archive and restore follow
the note lifecycle rules described in [Notes](/FollowThrough.ai/subsystems/notes/).

## Evidence

Controller tests cover normalized details and tree presentation. Creation controller tests cover explicit
project scope, parent validation, document kinds and stable identities. PostgreSQL contracts cover
root moves after reload, restoration from an archived folder, cleared descriptions and caller-assigned
folder identities. Offline creation tests cover the same sibling-count rule.
