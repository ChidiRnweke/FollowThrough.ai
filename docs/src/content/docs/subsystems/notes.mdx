The notes capability follows the standard layering: `src/lib/models/notes/` → `src/lib/server/services/notes/` → `src/lib/server/controllers/notes/` → `src/lib/server/repositories/notes/`. Two things make it more than CRUD: a write path that keeps derived state consistent in the same transaction, and an offline-first sync protocol that runs through IndexedDB on the client.

## Model

`Note` carries a ProseMirror `document`, its derived `plainText`, and two revision counters: `currentRevision` bumps on every content save, `publishedRevision` marks the last publish. An ETag is derived, never stored: `note:<id>:r<currentRevision>` (`noteEtag` in the model), so any holder of a note can compute the token a save must present. `noteSyncContentEquals` compares title, plainText, pin, and document — deliberately not timestamps — so a retried save that already landed compares equal to the remote.

`NoteSyncRecord` is the client's three-way state for a note: `base` (last version both sides agreed on), `local` (device copy), optional `remote` (diverged server copy), and a state of `synced | pending | syncing | conflict`. `NoteSyncStatus` adds the UI-only `loading`, `saving`, and `error`.

## The save transaction

`NotesController.save` runs inside the transaction runner and does four things atomically:

1. `NoteCatalog.save` validates and writes: non-empty title, a well-formed ProseMirror document (`findProseMirrorDocumentIssue`), not archived, and `projectId`/`kind` immutable — a save can never move a note between projects or turn it into a folder, and folders cannot hold authored content. Concurrency is optimistic: the candidate must carry the current revision, and the write itself is `updateIfRevision`, so a concurrent save loses with `StaleRevisionError` rather than overwriting.
2. Source anchors whose quote is still unique in the new text are re-pointed (`repairForNote`).
3. Note links are reconciled: `collectNoteLinkTargets` walks the document for `noteLink` marks, and the `mentions` rows are rewritten to match. The document is the source of truth for links; the relationships table is a derived index, so this runs in the transaction — committing a body without its derived rows would show backlinks the note no longer has.
4. The note is re-indexed for search.

The read side (`get`) is the opposite shape: note, relationships, references, diagrams, todos, and pending suggestions are fetched in parallel and assembled into a `NoteView` carrying the note's ETag.

## Sync and conflicts

`sync` is the offline client's write path. It validates that the submitted note matches its `baseEtag`, then delegates to `save`. A `StaleRevisionError` is not automatically a conflict: the controller re-reads the remote, and if `noteSyncContentEquals(remote, submitted)` the outcome is `saved` — retrying a save that actually landed is never reported as a conflict. Only genuine divergence returns `conflict` with the remote version.

On the client, `NoteSyncCoordinator` (`src/lib/client/notes/sync/`) keeps one `NoteSyncRecord` per note in IndexedDB and drives it through the states: `stage` records an edit as `pending`, `flush` sends it, and any divergence — detected on open, on flush, or on the server's conflict reply — lands the record in `conflict` with the remote attached. Resolution is a whole-document choice: `useRemote` adopts the server version; `keepLocal` rebases the local document onto the remote revision and re-stages it as `pending`. The store retries on `online` and when the tab becomes visible, and `listSyncInventory` gives a project-wide ETag listing so a returning client can diff its device state against the server.

Publish guards on the ETag, records a `NoteRevision`, and marks `publishedRevision`; `discardDraft` restores the latest recorded revision and throws `NotFoundError` when none exists.

## Import

`NoteImportsController` (`src/lib/server/controllers/imports/`) bulk-imports a zip of Markdown. It is deliberately **not** transactional: a vault with three malformed files imports the rest and reports the three, because a partial import that reports itself is recoverable and a full rollback is the wrong trade for onboarding. Archive reading is pure and defensive: an archive over 25 MB or 2,000 entries, or one carrying a path that escapes the root, is rejected outright — and sizes are checked against *declared* headers before anything decompresses — while individual files past the per-file limits (1 MB, 8 folders deep, Markdown only) are skipped and reported. Creation runs in two passes: every note is created and titled first (file name names the note; ` (2)` suffixes resolve collisions within a folder), then bodies are written with `[[wiki links]]` resolved against the now-complete title map — a vault's links point both directions, so only after every note exists is every title resolvable. Unresolved links stay as the author wrote them. Frontmatter is stripped and its unmapped keys reported.

Markdown conversion is isomorphic: `noteContentFromMarkdown` is shared between the server and the browser, so the agent's patch preview renders exactly what the server will apply. `note-patch.ts` applies agent edits as exact-string anchors — a non-unique or missing anchor fails loudly instead of applying at the wrong offset.

## Inline diagrams

Mermaid blocks live in the document as nodes; rendering is themed to the app's tokens and sanitized with DOMPurify under mermaid's `strict` security level, and renders that would otherwise disturb page layout (copy, export) run in a fixed off-screen host. Generating a diagram from a selection creates a `diagram` suggestion with anchor and provenance in one transaction. Converting one to draw.io goes through the agent, validates the returned XML, and offers the draft as a suggestion; accepting it (with the review dialog's edited XML and SVG) persists the draw.io diagram, and the editor swaps the pending-conversion node for a reference to it. See [agent](/FollowThrough.ai/subsystems/agent/) for the run pipeline behind the conversion and the accept/reject lifecycle that suggestions share.

Pasted or dropped images upload through [attachments](/FollowThrough.ai/subsystems/attachments/); the document stores the stable content endpoint, never the expiring upload URL.

## Invariants callers rely on

- A save and all its side effects — anchors, links, index — commit together or not at all.
- Revision is the only concurrency token; content equality, not timing, decides whether a stale base was a retry or a conflict.
- Conflict resolution always preserves a complete rich document; there is no partial merge.
- Import is additive: a name collision never merges or overwrites an existing note.
