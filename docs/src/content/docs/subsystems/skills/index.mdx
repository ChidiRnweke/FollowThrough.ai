A skill is a reusable instruction set the agent loads on cue. The instruction text lives in an ordinary note with `kind: 'skill'`; everything the agent uses to decide _whether_ to load it (name, slug, description, trigger hints, enable flag) lives in a `skills` row keyed by that note's ID. The agent never sees full skill text up front: `AgentContext` packs summaries into a 16,000-character catalog in the system prompt, and the model pulls the full instructions with the locked `load_skill` tool, which records a usage row as a side effect. Versioning comes free from the notes subsystem, pinning is per project, and three built-in skills provision themselves on first listing.

Skills are the user-facing half of how the agent grounds itself; see [using the agent](/FollowThrough.ai/using/the-agent/) for what loading a skill looks like from the chat side.

## Why this subsystem exists

Two problems fall out of "let users write their own agent instructions." First, context is finite: a workspace can accumulate hundreds of skills, so the full text of every skill cannot go into every system prompt, which means discovery has to be cheap and loading has to be a deliberate act. Second, accountability: once the agent follows user-written instructions, you need to know _which_ instructions shaped a given answer. The split design below (summaries always advertised, full text behind a tool call that writes a `skill_usages` row) answers both.

## Where things live

- **Models**: `src/lib/models/skills/index.ts`: `Skill` (the note plus its metadata), `SkillSummary` (the advertised projection: name, slug, description, trigger hints, `allowImplicitInvocation`, `isEnabled`, pin state), `SkillManifest` (the portable SKILL.md form), `SkillUsage` (one record per agent load).
- **Services**: `src/lib/server/services/skills/`: `SkillLibrary` (`library.ts`) implements every contract in `contracts.ts`; `SkillManifestCodec` (`manifest.ts`) parses and serializes SKILL.md; `BuiltInSkills` and the `BuiltInSkillLibrary` wrapper (`built-ins.ts`) provision the shipped skills from `built-in-definitions.ts`.
- **Controllers**: `src/lib/server/controllers/skills/controller.ts`: `Skills` is the public surface: listing, editing, versioning, pinning, and the agent-facing `loadForAgent`, which is `get` plus a usage record.
- **Repositories**: `src/lib/server/repositories/skills/postgres/skills.ts`: `SkillRecords` owns all SQL over three tables and maps rows to models on the way out.

The user-facing surface is small: `/skills` lists the catalog and `/skills/[id]` edits one skill, with SKILL.md import through the remote functions in `src/lib/remote/skills/skills.remote.ts`.

## Storage: a note plus a metadata row

Skills reuse the notes subsystem for everything that already works there: the document, revision history, autosave, sync. The `skills` table (`src/lib/server/db/schema/registry.ts:408`) uses the note ID as its primary key with cascade delete, so deleting the note deletes the skill row with it. `project_skill_pins` is a composite-key join table, and pinning is idempotent (`onConflictDoNothing`). `skill_usages` keeps `contextNoteId` and `provenanceId` as set-null references, so usage history survives deletion of the note a skill was applied against. Every read joins through projects and excludes archived ones.

`SkillManifestCodec` parses SKILL.md as YAML frontmatter (`name`, `description`, optional `license`, `compatibility`, `metadata`) followed by the instruction body. Limits are enforced by zod: slugs are lowercase-hyphenated and at most 64 characters, descriptions at most 1024, compatibility at most 500 (`manifest.ts`). The reserved metadata key `followthrough.allow-implicit-invocation` maps to `allowImplicitInvocation: false` and is stripped from user metadata on parse: it is a flag riding in metadata, not user data.

## How the agent discovers and loads a skill

Discovery is a two-step design: summaries are cheap and always advertised; full instructions cost a tool call and are recorded.

	source={`

	catalog --> filter["keep: enabled and (implicit or requested)"]
	filter --> order["order: requested → pinned → alphabetical"]

	load --> usage["loadForAgent records skill_usages"]

1. `AgentContext` (`src/lib/server/services/agent/runs/context.ts:78`) calls `listEnabled` on the provisioned finder, then keeps skills that are enabled and either allow implicit invocation or were explicitly requested by name, slug, or note ID (`context.ts:125`).
2. The catalog is ordered requested → pinned in the current project → alphabetical, then packed into a 16,000-character JSON budget (`SKILL_CATALOG_BUDGET`, `context.ts:43`). Requested and pinned entries are never dropped; when the rest overflow, the catalog is marked truncated and the prompt says the remainder is reachable through `list_skills`. Ordering is deterministic so the prompt is stable between runs.
3. `reasoning.ts:514` renders the catalog as a `<skills>` section in the system prompt, explicitly tagged as untrusted data, with the instruction to call `load_skill` for whatever applies.
4. `load_skill` calls `SkillsController.loadForAgent`, which is `get` plus a side effect: a `skill_usages` row linking the skill to the run's provenance record and the note it was applied against (`controller.ts:98`). That write is what makes "which skills actually get used" answerable later.

## Editing, versioning, pinning

`SkillLibrary` (`library.ts`) holds the rules callers rely on:

- **Creation converts a note.** `create` rejects folders, derives the slug from the name, and rejects a slug that collides with any of the user's other skills. A blank description becomes `Reusable instructions for {name}.`
- **Selection distillation checks out the exact text.** `createFromSelection` rejects the input unless the selection's revision, offsets, and text all match the source note's _current_ state, and the provenance record must already exist. The controller records the selection anchor and provenance first, in the same transaction (`controller.ts:125`), so every distilled skill carries a traceable lineage.
- **Content edits and metadata edits are different operations.** `update` rejects a call that carries both `raw` SKILL.md and a structured manifest. A metadata-only update (name, description, trigger hints, enable flag) never touches the note's document or revision history: the body belongs to the note sync path. A manifest update rewrites the body and appends a new revision.
- **History is append-only.** `restoreVersion` copies an old snapshot forward as a _new_ current revision (and restores its attachment snapshot) instead of rewinding.
- **Pinning is per project.** A pinned skill leads the advertised catalog in that project and is never budget-dropped. Pin state resolves through the `project_skill_pins` join for the requested project.

## The agent tool catalog

Every `SkillsController` method is classified in `agentToolCoverage` (`src/lib/server/agent-tool-factory.ts:199`): `list_skills`, `load_skill`, `create_skill`, `create_skill_from_selection`, `list_skill_versions`, `restore_skill_version`, `update_skill`, `set_skill_pinned`. Reads stay reads, creation and edits are mutations, and `get` and `serialize` are the exclusions: skill reads go through `load_skill`, and the full skill is already reachable there. `load_skill` is also first-class (`FIRST_CLASS_TOOL_NAMES`, `agent-tool-factory.ts:58`): offered directly without going through `search_tools`. The same coverage feeds the MCP surface, so an external host sees the identical skill tools.

## Built-in skills

Three built-ins ship in `built-in-definitions.ts`, FollowThrough (the product guide), Settings, and Diagramming, plus verbatim retired bodies of earlier releases. `BuiltInSkills.ensure` provisions them into the user's default project, repairs their kind/project/archived state, and adopts a legacy note titled "followthrough" if one exists.

Upgrades are conservative: a stored built-in is replaced by a newer definition only when it still matches a retired release byte-for-byte and was never published: an install the user never edited (`built-ins.ts:133`). Any user edit pins the skill to its current content forever. Retired bodies are never edited in place, because they exist to recognize those installs.

`BuiltInSkillLibrary` wraps the plain finder and calls `ensure` before every `listEnabled`/`listAll`, so built-ins simply appear. The diagramming pipeline is the one consumer that loads a built-in by key (`load(actor, 'diagramming')` in `src/lib/server/services/diagrams/authoring.ts:387`) and that load refuses a skill the user has disabled. The Diagramming definition sets `allowImplicitInvocation: false`, so it is advertised to the agent only when explicitly requested.

Composition lives in `createSkillsCapability` (`src/lib/server/skills-capability-factory.ts`): one repository wired into `SkillLibrary`, `BuiltInSkills`, and the `BuiltInSkillLibrary` wrapper. In `application.ts` the controller's `skillFinder` is the provisioned wrapper (built-ins ensured on every listing) while editing, usage, and versioning go straight to the plain library.

## What holds

- A skill's body is a note; the `skills` row is metadata only, and dies with the note (cascade on the shared key).
- The agent never receives full skill text in the system prompt: only summaries, within the 16,000-character budget, with requested and pinned entries immune to truncation.
- Every agent load is recorded in `skill_usages` with provenance; the UI reads skill bodies through the controller, outside the agent tools, so its reads never count as usage.
- Metadata-only edits never create note revisions; content edits always do.
- `load_skill` is locked on (`LOCKED_TOOL_NAMES`, `agent-tool-factory.ts:79`): the user cannot deselect it, because without it the agent loses its instructions.
