A note is a ProseMirror document plus a revision counter. Every save runs in one transaction that also repairs source anchors, rewrites the derived link rows, and re-indexes the note for search, so the body and its derived state can never diverge. Offline edits use the shared workspace outbox. Each operation carries its identity and observed resource version. A durable server receipt proves whether that exact operation applied; matching note content does not establish acknowledgement. Bulk import takes a zip of Markdown (a "vault") and is deliberately **not** transactional, with hard limits checked against declared archive sizes before anything decompresses.

User-facing behavior: [Notes](/FollowThrough.ai/using/notes/).

## Why this subsystem exists

Notes are the substrate everything else sits on: todos extract from them, memory and suggestions anchor to passages in them, search indexes them, the agent edits them. That means a note write is never just a row update: anchors must follow edited text, backlink rows must match the document that landed, and the search index must reflect the new body. Doing those in separate writes would leave windows where the graph disagrees with the document, so they share one transaction. And because users edit offline, the write path is also a sync protocol.

## The layers

- **Models**: `src/lib/models/notes/` contains note values, request types and schemas. Remaining document and edit helpers are still being moved to their owners.
- **Shared services**: `src/lib/services/notes/presentation.ts` assembles note views and computes revision tokens for server and downloaded records.
- **Server services**: `NoteCatalog` validates and writes notes. Focused services handle anchors, relationships and indexing.
- **Controllers**: `Notes` coordinates saves, synchronization, publication, archive import and view assembly. `WorkspaceViews` assembles downloaded views.
- **Repositories**: note repositories own Drizzle access, including the compare-and-swap write `updateIfRevision`.
- **Client**: `src/lib/client/sync/` owns IndexedDB storage, the outbox and the account workspace runtime.

## The save transaction

`Notes.save` does four things atomically:

1. `NoteCatalog.save` validates and writes: non-empty title, a well-formed ProseMirror document, not archived, `projectId`/`kind` immutable: a save can never move a note between projects or turn it into a folder, and folders cannot hold authored content. Concurrency is optimistic: the candidate must carry the current revision, and the write is `updateIfRevision`, so a concurrent save loses with `StaleRevisionError` instead of overwriting.
2. `repairForNote` re-points source anchors whose quote is still unique in the new text.
3. `noteLinkReconciler.reconcile` rewrites the `mentions` rows to match `collectNoteLinkTargets(document)`. The document is the source of truth for links; the relationships table is a derived index, so this runs in the transaction: committing a body without its derived rows would show backlinks the note no longer has.
4. `noteIndexer.index` re-indexes the note into the knowledge-search retrieval index: this is how note content becomes searchable; archive and rename re-index too, so archived notes drop out of results.

The read side (`get`) is the opposite shape: note, relationships, references, diagrams, todos, and pending suggestions are fetched in parallel and assembled into a `NoteView` carrying the note's ETag.

## Offline synchronization

A browser edit enters the workspace outbox before local save reports success. The operation keeps its identity, normalized command and observed resource version. The server's `Notes.synchronize` coordinates the operation lock, version check, note write and durable receipt in one transaction. Retrying the same operation cannot apply it twice.

The resource version used by workspace synchronization is distinct from the note revision used by publication. `noteEtag(note)` in `services/notes/presentation.ts` returns `note:<id>:r<currentRevision>`. Publishing rejects a token for a different note or revision.

## Publish and drafts

`currentRevision` bumps on every content save; `publishedRevision` marks the last publish. `publish` guards on the ETag (`StaleRevisionError` if the note changed since it was loaded), records a `NoteRevision`, and marks `publishedRevision`: in one transaction. `discardDraft` restores the latest recorded revision's title/document/plainText through the normal save path, and throws `NotFoundError` when no published revision exists yet. `rename` also records a revision and re-indexes, so a rename is restorable the same way.

## Vault import

The remote archive reader prepares Markdown entries, then `Notes.importMarkdownArchive` creates notes and resolves links. The whole import is deliberately **not** transactional: a vault with three malformed files imports the rest and reports the three. Each note save still commits its own derived state atomically.

Archive reading (`src/lib/remote/notes/archive-reader.server.ts`) checks the **declared** uncompressed sizes in the zip headers before decompressing entries:

- Whole-archive rejections: over 25 MB total (`maxTotalBytes`), over 2,000 entries (`maxEntries`), or any path that escapes the root (`..` segments, with backslashes folded to `/` so Windows-style archives can't smuggle traversal past the check).
- Per-file skips, reported not fatal: larger than 1 MB, nested deeper than 8 folders, not Markdown (`.md`, `.markdown`, `.mdx`).
- Ignored outright: `__MACOSX/`, `.git/`, `.obsidian/`, `.trash/`, and any dotfile or dot-directory anywhere in the path.

Creation runs in two passes: notes are created and titled first, then bodies are written. `indexArchiveReferences` and `resolveArchiveLinks` in the import service resolve wiki links against original archive paths and titles, including records of failed imports. Display-name collision suffixes do not change that source identity. Relative paths resolve from the source folder. Ambiguous, missing and failed targets remain as written and appear in the import report. YAML frontmatter is stripped and its keys reported as unmapped.

## What always holds

- A save and all its side effects (anchors, links, index) commit together or not at all.
- Note revisions guard direct note writes and publication. Workspace resource versions guard offline operations; durable receipts identify retries.
- Conflict resolution always preserves a complete rich document; there is no partial merge.
- Import is additive: a name collision never merges or overwrites an existing note.
- The ETag is computable from any copy of the note: `note:<id>:r<currentRevision>`.

## What depends on this

- [Todos](/FollowThrough.ai/subsystems/todos/): promise extraction anchors to a note revision; `get`'s parallel read assembles the note's todos.
- [Memory](/FollowThrough.ai/subsystems/memory/) and suggestions: memory and todo suggestions reuse the provenance/anchor machinery defined by notes.
- [Search](/FollowThrough.ai/subsystems/search/): the save transaction re-indexes the note into the retrieval index; archiving re-indexes so archived notes drop out.
- [Agent](/FollowThrough.ai/subsystems/agent/): the agent edits notes through patch anchors and proposes diagram conversions as suggestions.
- [Attachments](/FollowThrough.ai/subsystems/attachments/): pasted or dropped images upload through attachments; the document stores the stable content endpoint, never the expiring upload URL.
