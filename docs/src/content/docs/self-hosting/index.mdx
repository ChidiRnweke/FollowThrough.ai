The hosted instance is in closed beta; the repository is MIT-licensed, so the way in today is to run it yourself. Everything ships as **one container image** (`Dockerfile`, node:22-alpine, multi-stage): the web process serves `build/` on `:3000`, and the worker sidecar runs `build-worker/worker.js` from the same image. The app needs PostgreSQL 17 with pgvector, an S3-compatible object store, an OpenRouter key, and a Mistral key. Configuration comes from an Infisical project by default, or from plain environment variables with `CONFIG_SOURCE=env`. The production path is three commands: create the external networks, run the one-shot `migrate` service under the `setup` profile, then bring up `app` and `worker`.

The architecture this guide assembles (the layered capability design, the agent run pipeline, the worker's role) is documented under [architecture](/FollowThrough.ai/explanation/architecture/).

Do whatever you want with the code: self-host it, fork it, strip it for parts. Three asks if you do: tell [the author](https://github.com/ChidiRnweke) you're running it (what you use it for shapes what gets built next), star [the repository](https://github.com/ChidiRnweke/FollowThrough.ai), and keep the copyright notice in the LICENSE file. That last one is the license talking, not a favour.

## What you need

- **Docker**: the app image, the database, and the object store all run as containers.
- **PostgreSQL 17 with pgvector**: every note, todo, memory entry, and embedding lives here. The dev compose file uses `pgvector/pgvector:pg17`.
- **An S3-compatible object store**: attachments and documents. The dev compose file uses [RustFS](https://rustfs.com); anything S3-compatible works.
- **An OpenRouter API key**: every model the agent and the pipelines run is reached through OpenRouter.
- **A Mistral API key**: OCR on attachments, called directly rather than through OpenRouter. Documents are fetched from a presigned object-storage URL, so the bucket must be reachable from Mistral.
- **An Infisical project**: the default secrets backend; `scripts/provision-db.js` also writes the provisioned `DATABASE_URL` back into it. Skip it entirely with `CONFIG_SOURCE=env`.
- **An OIDC provider**: sign-in is wired against Authentik. All deployments, including local development, require `AUTHENTIK_DOMAIN`, `AUTHENTIK_CLIENT_ID`, `AUTHENTIK_CLIENT_SECRET`, and `AUTHENTIK_CALLBACK_URL`. Missing or blank values fail startup. There is no unauthenticated single-user mode.

Both processes run the same application graph and the same configuration; the worker serves no HTTP and instead ticks the periodic background tasks the request path hands off: search-index maintenance, attachment retention, and [scheduled runs](/FollowThrough.ai/using/scheduled-runs/) (`src/worker.ts`). Keep it at **one replica**: the tasks discover their work from the database on every tick, so a second replica only duplicates embedding calls.

The worker also runs the agent (ADR 0052). Every 30 seconds it starts the schedules that are due, each as its owner, so it calls OpenRouter and the user's connectors with the same configuration as the web process. Without a running worker no schedule starts; when the worker comes back, each schedule that missed its time runs once. A worker restart fails the scheduled runs it was executing, and each shows as a failed run that its owner can retry. A restart of the web process does not touch them.

Telemetry is optional but wired in from the start: both processes boot with `scripts/otel-instrumentation.js` and export OTLP to a collector (`OTEL_EXPORTER_OTLP_ENDPOINT`), which filters down to LLM/tool/agent spans and forwards them to Phoenix (`otel-collector-config.yaml`).

## The image

`Dockerfile` is a four-stage node:22-alpine build: `base` (pnpm via corepack) → `prod-deps` (production `node_modules`) → `builder` (`pnpm build`, which builds both the SvelteKit app and the worker entrypoint via `vite.config.worker.ts`) → `runtime`. The runtime stage carries `build/`, `build-worker/`, `drizzle/` (the migration SQL), `scripts/` (migration and provisioning), and `assets/` (embedded fonts for PDF export): everything the app, the worker, and the one-shot migrate job need, in one image. The default command serves the app on `:3000` through `scripts/start-web.js`, which waits for active HTTP requests before shutting down telemetry; the worker is the same image with `command: ['node', '--import', './scripts/otel-instrumentation.js', 'build-worker/worker.js']`.

## Configuration: bootstrap vs application

Configuration is layered, and the two example files map exactly onto the layers:

- **Bootstrap** (`.env.example`): five values telling the app where its secrets live: `CONFIG_SOURCE` plus the `INFISICAL_CLIENT_ID` / `CLIENT_SECRET` / `PROJECT_ID` / `ENVIRONMENT` / `URL`. This file stays on the host; nothing application-specific goes in it.
- **Application** (`.env.infiscal.example`): everything else, imported into the root of the Infisical project. Seven keys are required with no runtime default: `DATABASE_URL`, `OPENROUTER_API_KEY`, `MISTRAL_API_KEY`, `AUTHENTIK_DOMAIN`, `AUTHENTIK_CLIENT_ID`, `AUTHENTIK_CLIENT_SECRET`, and `AUTHENTIK_CALLBACK_URL`. The rest (model choices, S3 credentials, retrieval chunking, archive admission) have defaults in `APPLICATION_DEFAULTS` (`src/lib/server/config.ts`) and can be omitted.

`CONFIG_SOURCE=env` collapses the two layers: application keys are read straight from the process environment and no Infisical client is created. That is the simple path for a small deployment; Infisical earns its keep when you want secrets rotated outside the deployment or shared between the app and the provisioning script.

## Run it

<Steps>

1. **Clone and set the bootstrap environment.**

   ```sh
   git clone https://github.com/ChidiRnweke/FollowThrough.ai.git
   cd FollowThrough.ai
   cp .env.example .env   # fill in the INFISICAL_* values, or set CONFIG_SOURCE=env
   ```

2. **Stand up PostgreSQL 17 + pgvector and an S3-compatible store.**

   For a local deployment the dev compose file provides both, plus an OTLP collector:

   ```sh
   docker compose up -d postgres rustfs
   ```

   That gives you Postgres on `:5432` and RustFS on `:9000` (console on `:9001`) with the credentials `APPLICATION_DEFAULTS` already expects. For an existing database or bucket, set `DATABASE_URL` and the `S3_*` keys yourself and skip this step.

3. **Put the application config where the app will read it.**

   With Infisical: import `.env.infiscal.example` into your project and replace `OPENROUTER_API_KEY`, `MISTRAL_API_KEY`, `DATABASE_URL`, and all four `AUTHENTIK_*` values (the database URL can be omitted if you let provisioning create it: next step). With `CONFIG_SOURCE=env`: export the same keys into the environment.

4. **Provision and migrate the database (one shot).**

   The production compose file carries a `migrate` service under the `setup` profile that runs `scripts/provision-db.js` (creates the database and role with a random password, grants privileges, and stores the resulting `DATABASE_URL` in Infisical: skipped entirely if `DATABASE_URL` already exists there) followed by `scripts/prod-migrate.js` (Drizzle migrations from `./drizzle`, then seeds the `tool_embeddings` table used by agent tool search — only changed tool descriptions are re-embedded, so reruns are cheap):

   ```sh
   docker compose -f docker-compose.prod.yml --profile setup run --rm migrate
   ```

5. **Start the app and the worker.**

   ```sh
   docker compose -f docker-compose.prod.yml up -d app worker
   ```

   The app listens on `:3000`. Put your reverse proxy in front of it, set `ORIGIN` to the public URL, and configure the four required `AUTHENTIK_*` values. The callback URL must match the one registered with Authentik.

</Steps>

<Aside type="note">

The shipped `docker-compose.prod.yml` is the author's own deployment: it pulls the published image from GHCR, reads secrets from Infisical, joins four **external** Docker networks (`reverse-proxy`, `postgres-network`, `rustfs-network`, `telemetry-network`; create them with `docker network create` or rewrite the `networks:` block), carries Caddy labels for his reverse proxy, and is reconciled by Komodo (the `komodo.skip` label on the migrate job). Treat it as a reference for how the pieces fit together, not as the only way to run the stack: any arrangement that gives both processes the same configuration, the database, and the bucket works.

</Aside>

## Connectors

Connectors let the agent call the remote MCP servers of other services, such as Linear or Notion (ADR 0049). They are off until you set `CONNECTOR_SECRET_KEYS`. Without it, **Settings > Connectors** says connectors are not set up, and no run is offered a connector tool.

- **The keyring.** `CONNECTOR_SECRET_KEYS` is a comma-separated list of `<keyId>:<key>` entries. A key id is 1 to 16 lowercase letters or digits. A key is 32 random bytes in base64: `openssl rand -base64 32`. FollowThrough encrypts every stored sign-in with AES-256-GCM under the first key and can decrypt with any key in the list. A keyring that does not parse stops the app at startup.
- **Rotation.** Put the new key first and keep the old one after it: `v2:<new>,v1:<old>`. A sign-in moves to the new key the next time its token is renewed. If you remove a key while sign-ins still use it, those connectors show **Connect again** and stay listed; nothing is deleted, and signing in again stores the sign-in under the current key.
- **Client registration.** FollowThrough registers itself with each service automatically. When `ORIGIN` is a public HTTPS address and the service supports it, FollowThrough identifies itself with the client ID metadata document at `/oauth/client-metadata.json`, which the service fetches. That path is public by design. Otherwise, for example on `localhost`, it uses dynamic client registration.
- **Services that need your own client.** Some services offer neither, so each needs an OAuth app that you register with that service. Set the app's callback URL to `<ORIGIN>/connectors/callback`, then set the service's two keys below. Set both or neither: one without the other stops the app at startup. Until both are set, the service does not appear in the catalog at all.

  | Service   | Keys                                                                 |
  | --------- | -------------------------------------------------------------------- |
  | Asana     | `CONNECTOR_ASANA_CLIENT_ID`, `CONNECTOR_ASANA_CLIENT_SECRET`         |
  | Box       | `CONNECTOR_BOX_CLIENT_ID`, `CONNECTOR_BOX_CLIENT_SECRET`             |
  | GitHub    | `CONNECTOR_GITHUB_CLIENT_ID`, `CONNECTOR_GITHUB_CLIENT_SECRET`       |
  | HubSpot   | `CONNECTOR_HUBSPOT_CLIENT_ID`, `CONNECTOR_HUBSPOT_CLIENT_SECRET`     |
  | PagerDuty | `CONNECTOR_PAGERDUTY_CLIENT_ID`, `CONNECTOR_PAGERDUTY_CLIENT_SECRET` |
  | Render    | `CONNECTOR_RENDER_CLIENT_ID`, `CONNECTOR_RENDER_CLIENT_SECRET`       |
  | Slack     | `CONNECTOR_SLACK_CLIENT_ID`, `CONNECTOR_SLACK_CLIENT_SECRET`         |

- **Network.** Connector traffic goes out over HTTPS only. FollowThrough refuses any server whose address resolves to a private, loopback, link-local, or metadata network, and it follows a redirect only to the same origin. A custom server must therefore be reachable on the public internet.

## Day two

- **Upgrades** are pull-and-restart plus a re-run of the `setup`-profile migrate step; migrations are ordinary Drizzle SQL under `drizzle/`.
- **Provisioning is idempotent**: `provision-db.js` fails closed: a listing failure against Infisical is never read as "no secret", so re-running it cannot rotate the password of a database it cannot see.
- **Authentication is mandatory**: deployments that previously used anonymous single-user access must configure Authentik before upgrading. `LOCAL_USER_ID` no longer selects a runtime account. Existing account data is retained, but this change does not link or transfer it to a new Authentik account. MCP clients always require a FollowThrough API token.

## Request and archive admission

`BODY_SIZE_LIMIT` remains the adapter-node HTTP request limit (52,428,800 bytes in the reference deployment). Direct object-storage uploads do not pass through that HTTP body. Application-level attachment, chat-image, screenshot, diagram, and export-image size ceilings are removed; upstream failures are reported explicitly.

Archive import checks the expanded total that the archive declares before decompression, then counts the bytes each entry actually inflates to against the same limit. `ARCHIVE_MAX_EXPANDED_BYTES` defaults to 26,214,400 and `ARCHIVE_MAX_ENTRIES` to 2,000. Both must be positive safe integers. An archive exceeding either setting is rejected with the setting named. An uploaded file larger than `ARCHIVE_MAX_EXPANDED_BYTES` is rejected before it is read, because a deflated archive is not meaningfully larger than its expanded content. A Markdown file whose inflated size or checksum differs from what the archive declares is reported as skipped, and the rest of the archive imports. There is no separate per-note size or folder-depth ceiling.

DOCX templates have their own admission settings, which default to the archive values because a template is the same kind of ZIP package. `TEMPLATE_MAX_BYTES` (26,214,400) limits the uploaded file: a larger upload is refused when it is reserved, and completion reads no more than this from storage. `TEMPLATE_MAX_EXPANDED_BYTES` (26,214,400) limits the bytes the template's parts inflate to while its styles are read, and `TEMPLATE_MAX_ENTRIES` (2,000) limits its number of parts. All three must be positive safe integers. A template exceeding any of them, or with a part whose size or checksum differs from what the package declares, is refused with the reason named.

Three small endpoints read at most a fixed number of body bytes and answer `413` past it, whatever `Content-Length` says. Each default admits the largest request the endpoint's schema accepts, with every character in its longest encoding:

| Setting                             | Default | Endpoint                                          |
| ----------------------------------- | ------- | ------------------------------------------------- |
| `CLIENT_ERROR_MAX_BODY_BYTES`       | 66,560  | `/api/client-errors`, browser error reports       |
| `OAUTH_REGISTRATION_MAX_BODY_BYTES` | 491,520 | `/oauth/register`, MCP client registration        |
| `OAUTH_TOKEN_MAX_BODY_BYTES`        | 221,184 | `/oauth/token`, MCP code and refresh token grants |

Each signed-in user may send `CLIENT_ERROR_REPORTS_PER_WINDOW` browser error reports (default 20, one page's own cap) per `CLIENT_ERROR_WINDOW_SECONDS` (default 60). A repeat of a report already logged in the window is dropped; the next logged report says how many were dropped. A report past the budget is answered `429` with `Retry-After`. All five settings must be positive safe integers.

Each connector operation has one total deadline: listing a server's tools across every page, discovering and completing OAuth sign-in, refreshing a token, or fetching a server's icon. `CONNECTOR_OPERATION_TIMEOUT_MS` defaults to 60,000, the MCP SDK's default timeout for a single request, and must be a positive safe integer. An operation that passes it fails with the setting named and keeps no partial tool list; an icon that passes it leaves the connector with its monogram. Connector requests never go to a special-use address, whether a host name resolves to one or the URL names one as an address literal.

## Sign-in and MCP client limits

Sign-in waits at most `AUTHENTIK_REQUEST_TIMEOUT_MS` (default 10,000) for each Authentik token or profile request. This is a starting value, not a measurement. A request that gets no answer in time fails the sign-in instead of holding the callback open. When Authentik answers with an error, the error message quotes at most the first 500 bytes of its body.

MCP clients without a metadata document register anonymously through `/oauth/register` (ADR 0050). A registration is used each time the user approves the client and a code is issued to it. The worker deletes a registration that has not been used for `MCP_CLIENT_UNUSED_RETENTION_MS` (default 86,400,000, one day) and that no live connection or pending code names. This is a starting value: a client normally uses its registration within the 60-second code lifetime of the flow that created it, and one day leaves room for a user who abandons the consent screen and comes back later. A client whose registration was deleted is refused as unregistered and registers again. `MCP_CLIENT_SWEEP_INTERVAL_MS` (default 900,000, fifteen minutes) sets how often the worker looks; this is also a starting value. All three settings must be positive safe integers.
