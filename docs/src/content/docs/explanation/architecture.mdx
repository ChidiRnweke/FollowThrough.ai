FollowThrough is a SvelteKit (Svelte 5, TypeScript) monolith, organized capability-first: every layer is sliced by product capability (notes, todos, memory, agent) rather than by technology. It runs on PostgreSQL 17 with pgvector (Drizzle ORM), S3-compatible object storage, and OpenRouter for chat models and embeddings. One Docker image serves both the web app and a worker sidecar; secrets come from Infisical; traces go to Arize Phoenix over OpenTelemetry.

The enforcement-level rules live in `ARCHITECTURE.md` at the repository root; this page is the map.

The project follows a layered architecture, with each layer sliced by capability (`src/lib/**/<capability>/`):

1. **Models** (`src/lib/models/<cap>/`): the capability's data types and branded IDs. Models are leaf modules: a model never imports another capability's model. Foreign IDs appear as local structural aliases, so capabilities stay decoupled at the type level. [Reference](/FollowThrough.ai/reference/models/)
2. **Repositories** (`src/lib/server/repositories/<cap>/`): own all persistence. They are the only place Drizzle and SQL exist, and they map rows to models immediately, so nothing above them ever sees a database row. Each capability declares a repository _contract_; the Postgres implementation satisfies it. [Reference](/FollowThrough.ai/reference/repositories/)
3. **Services** (`src/lib/server/services/<cap>/`): the business rules. A service imports models and repository contracts only; a service never imports another service, because two services coupling to each other is how business logic turns into spaghetti. Cross-service work goes one layer up. [Reference](/FollowThrough.ai/reference/services/)
4. **Controllers** (`src/lib/server/controllers/<cap>/`): thin orchestration. A controller receives an actor context and an input, coordinates the services needed to fulfil the request, and returns a result. The `<Capability>Controller` interfaces are the product's documented public surface: they are what the [API reference](/FollowThrough.ai/reference/controllers/) renders, and what the agent's tools wrap.

Delivery boundaries (SvelteKit routes and remote functions in `src/lib/remote/<cap>/`) delegate to controllers. On the client, each capability mirrors the same slice: remote / client / stores / components. The whole graph is composed in `src/lib/server/application.ts`, which calls each capability's `create<Capability>Capability` factory in dependency order and assembles the controller facade.

### Key features and modules

These layers are used to build the product's capabilities:

1. **Agent**: durable chat runs, approvals, and the tool catalog that wraps every controller. [Read more](/FollowThrough.ai/subsystems/agent/)
2. **Todos**: the commitment board: extract promises from notes, triage on Today, track who you're waiting on. [Read more](/FollowThrough.ai/subsystems/todos/)
3. **Notes**: the TipTap editor, autosave with ETag sync, publishing, and vault import. [Read more](/FollowThrough.ai/subsystems/notes/)
4. **Memory**: project- and profile-scoped durable facts for agents, written only through proposals. [Read more](/FollowThrough.ai/subsystems/memory/)
5. **Attachments**: uploads to object storage, Mistral OCR, and indexing into search. [Read more](/FollowThrough.ai/subsystems/attachments/)
6. **Knowledge search**: pgvector semantic indexing, retrieval, and reranking over notes, attachments, and memory. [Read more](/FollowThrough.ai/subsystems/search/)
7. **Projects**: the organizing unit every other capability hangs off. [Read more](/FollowThrough.ai/subsystems/projects/)
8. **Skills**: user-defined, versioned instruction sets the agent loads on cue. [Read more](/FollowThrough.ai/subsystems/skills/)
9. **Settings**: per-user and per-project resolution of models, tools, and trust policies. [Read more](/FollowThrough.ai/subsystems/settings/)

### Enforcement

The layering is not a convention: it is checked. `pnpm test:architecture` runs three checkers:

- **Topology audit** (`scripts/audit-topology.ts`): import direction, capability entry points, factory shape, and that maintained docs reference only existing paths.
- **Test-quality audit** (`scripts/audit-tests.ts`): no mocks or spies in server layers; hand-written fakes only.
- **chisel** (`chisel-js check`): architecture and design-system invariants with pointwise, justified exceptions.

A new controller method, a cross-service import, or an undocumented public symbol fails the build, not the code review.

One Docker image runs both processes: the web app and the worker sidecar, which composes the same application graph and runs background tasks (search-index maintenance, attachment retention) on a self-rescheduling interval. Tasks rediscover work from the database each tick, so a missed tick costs latency, not correctness.

Two separate authentication paths reach the same app, and neither substitutes for the other: a browser signs in through the OIDC provider (OAuth2, PKCE), while an MCP client authenticates with a Bearer API token minted in Settings. See [the agent](/FollowThrough.ai/subsystems/agent/) for how the same tool catalog serves both, and [Connect an MCP client](/FollowThrough.ai/guides/connect-mcp-client/) to set one up.

Configuration is hydrated from Infisical before the SvelteKit server starts; telemetry keys are the deliberate exception, supplied directly by the platform. Agent runs are instrumented end-to-end: every model call, tool call, and retrieval is one inspectable Phoenix trace. Deployment is Komodo-managed Docker Compose behind Caddy; see [Self-hosting](/FollowThrough.ai/self-hosting/) for running it yourself.
